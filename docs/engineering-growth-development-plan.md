# ReqFlow 工程成长闭环开发计划

编制日期：2026-10-10。依据：《ReqFlow_工程成长闭环_产品改造设计_v1.0.md》。

本计划只确定范围、顺序、依赖和验收，不估算工期。每批按“契约 → 迁移与后端 → 前端 → 联调与验收”完成，上一批提供可运行成果后再扩展下一批。原设计中的 PF / AC 编号沿用；新增任务单独列出。

## 1. 已确定的范围

- 先完成 P0 和 P1，使一项真实需求走通问题定义、任务执行、决策、验证、收尾、Wiki 复盘。
- P2 实践资产和 P3 作品档案放在 P1 验收、真实试用之后。
- 根据用户最新决定：前端 `dev` 的旧矩阵整体废弃，需求工作区成为唯一工程执行入口。无需维护旧矩阵交互或把新增能力接入旧矩阵。
- 旧矩阵废弃指页面、组件、重复 API 封装和遗留入口；现有需求、阶段、任务、依赖、Wiki 数据保留。
- 需求工作区内部的 `TaskMatrix.vue` 继续使用；后端 `/api/matrix/dependencies` 仍被新工作区调用，不能因名字包含 matrix 就删除。
- 保留快速创建和普通任务轻量操作；任务 DONE 与验证 PASS 分离；MVP 的 AI 能力只做人工填写的参与说明及基于事实的复盘模板整理。

## 4. M0：先解决实现前置

### 4.1 清理旧矩阵（新增 PF-007）

- 删除 `src/features/matrix/` 的旧页面、组件、composables、重复 API 封装，先确认不存在工作区外部导入。
- 移除 `MatrixLegacy` 专用路由及 `RequirementTable.vue` 中遗留 `go-matrix` 事件声明；核对调用点后清理对应命名和说明。
- 需求列表、待办、Wiki 反向链接统一跳转 `/requirements/:id`，按 `tab`、阶段、任务上下文定位。
- 保留新工作区任务矩阵、任务依赖接口、共享类型和底层数据；文案是否含“矩阵”不作为删除依据。
- 验收：无旧模块引用；类型检查与构建通过；需求进入工作区、待办定位任务、Wiki 回链、阶段/任务/依赖操作正常。旧 `/matrix` URL 不再承担业务入口。

### 4.2 契约、权限、迁移、状态（PF-001～006）

交付 `docs/engineering-growth-api-contract.md` 和决策清单，包含 DTO、请求/响应示例、错误码、枚举、分页、字段上限、资源关联校验、版本冲突以及更新语义。

| 需定案事项  | 推荐方案（尚未实施）                                         | 完成条件                                                                           |
| ----------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Schema 管理 | 沿用 Flyway + Hibernate validate                             | 核对实际 profile、环境覆盖、`flyway_schema_history`；演练 V1.0.5 升级与空库初始化  |
| 问题定义    | `definition_json` + 独立 GET/PUT/confirm 接口                | 不经旧需求全量更新接口保存；确认人/时间由服务端产生                                |
| 并发修改    | 定义采用原子版本比较；收尾检查关联记录版本                   | 两个编辑页面不能静默覆盖；确认请求也必须绑定所确认版本                             |
| 收尾        | 一需求一份独立 closeout 记录，保存结论、处置与 Wiki ID       | 不复制完整 Wiki 正文；明确草稿、完成、重新打开/待复核规则                          |
| 时间线      | 复用审计表作为事件列表，扩充类型、来源引用、筛选与服务端分页 | 正文从决策/验证实体获取；稳定排序；一次业务动作不重复展示审计与实体卡片            |
| 删除/修订   | 历史验证采用作废或带历史的修订，禁止无痕覆盖失败结果         | 区分新一轮验证与纠正录入；任务/阶段/需求删除时引用处理一致                         |
| 授权        | 需求权限继承 + 每个关联 ID 归属校验                          | 无项目需求、项目成员、创建人、分配人、无权限用户读写矩阵明确；客户端不提供作者身份 |
| 保存体验    | MVP 显式保存，失败保留输入，离开提示未保存                   | loading/empty/error/saved/unsaved/retry 与冲突恢复有统一行为                       |

### 4.3 最小测试与部署兼容基础（新增 PF-121、PF-120）

- 配置前端关键业务规则与组件测试、后端 Service/API 测试及 PostgreSQL 迁移集成测试；只覆盖会影响业务正确性的路径。
- 固定旧数据样本：无定义需求、旧任务、Wiki、跨项目成员和任务依赖。
- 客户端可连接不同版本自托管后端，需要明确定义新能力探测或最低后端版本；不兼容时明确提示并关闭新入口。
- 关闭新能力后保留需求、任务、Wiki 原流程；不恢复已经废弃的旧矩阵。
- 开始前记录 type-check/build/后端构建是否已有失败，区分基线问题与新增回归。

## 5. P1 各批任务与验收

### M1：问题定义（PF-101、102、103，PF-104 的定义部分）

后端：需求定义 JSONB migration、明确 DTO、读取/保存/确认接口、内容校验、版本冲突、变更使确认失效及审计。

前端：`RequirementDialog.vue` 保持轻量；增加“创建并定义问题”；概览中显示目标、成功标准、定义完整性及编辑入口。定义单独组件与 API，不把所有逻辑堆在概览里。

验收：AC-01～04、15～18 的相关场景。标题即可创建；刷新后仍可读；修改关键内容需重新确认；保存定义不清空旧描述、日期、状态、优先级、项目。

### M2：阶段和任务交付标准（PF-105；新增 PF-117）

阶段新增可选目标、预期产出、结束条件，落到 Stage 实体/DTO/migration、阶段 API、`StageEditor.vue`、`StageList.vue` 与保存 composable。创建仍保持轻量；任务数及完成数复用现有数据，待验证数在 M4 接入。

任务新增 `deliverable`、`completionCriteria`，覆盖 SubTask 存储、DTO、`TaskDetail.vue`、`TaskCreate.vue`、`useStageTasks.ts` 的 payload/响应/缓存。旧客户端省略新字段时必须保留；显式清空按契约执行。

验收：AC-05、16～18；新增阶段目标专项验收。填写后修改状态、排期、负责人不丢新字段；空字段任务可正常完成；任务树、依赖、个人待办仍正常。

### M3：决策（PF-106、107；新增 PF-118 的决策部分）

新增决策表、DTO、服务和接口；支持提案、采纳、否决、替代及替代关联，保留旧记录。决策保存和审计的一致性按 M0 方案落实。

复用一套决策抽屉，从需求概览、阶段上下文、任务详情打开；自动关联需求/阶段/任务。AI 参与说明作为可选结构化字段，由用户填写。

验收：AC-06、07、15～18；提案可无最终选择，采纳须有选择和理由；替代保留关联；篡改跨需求阶段/任务 ID 被拒绝。阶段级入口必须明确实现，不能只做概览和任务入口。

### M4：验证与概览（PF-108～110，PF-104 的验证部分；新增 PF-119）

后端：验证表、证据链接、标准快照、历史查询、分页和汇总接口；支持 PASS/FAIL/PARTIAL/INCONCLUSIVE/WAIVED，豁免须有理由。旧验证不可被新一轮验证覆盖。

前端：从任务/需求打开验证表单，展示最近结论及历史；概览展示标准验证分布和待处理项；阶段接入待验证数量。失败记录提供回到执行并创建修复任务的入口，自动带入上下文与来源引用。

必须固定的汇总规则：

- 成功标准使用稳定 ID，重排不改变 ID；实质修改须标记版本或失效关系。
- 修改/删除标准后仍保留旧描述快照与历史；旧 PASS 不自动证明新标准通过。
- “最新有效”使用明确排序及有效性规则；不能根据可回填的验证时间随意覆盖当前结论。M0 冻结排序，M4 实现并测试。
- 任务级验证不会在未绑定当前成功标准时自动变成需求级 PASS；任务待验证数和标准未验证数分开计算。
- 无记录是未验证，WAIVED 不是 PASS；DONE 不自动创建验证或变更验证结论。

验收：AC-08～11、15～18；重点验证 PASS→FAIL、失败→修复→重验、标准修改后的旧 PASS、同时间记录稳定排序及并发保存刷新。

### M5：活动与知识（PF-111、112；PF-201 的文档类型部分前移）

扩展 `RequirementActivity.vue` 与活动接口筛选：操作、决策、验证、知识沉淀；列表显示摘要、作者、上下文、事件时间和来源详情。使用服务端分页及稳定排序，不把多个 API 的第一页拼成全量时间线。

从决策/验证/任务发起 Wiki 编辑时，自动关联需求并提供事实摘要和来源链接；用户修改后才保存。文档类型在 P1 实现，旧文档显示“未分类”；直接 `projectId` 关联留在 P2。

任务/决策/验证来源先以可定位的内部链接和上下文传递表达；如确认需要长期结构化反向检索，在本批增加关联存储，而不是把关系藏进自由标签。

验收：AC-12、13、15、16；分页无同一事件重复卡片；从时间线跳转详情并刷新仍可定位；失败重试不丢 Wiki 草稿；旧 Wiki 正文、标签与分享行为不变。

### M6：收尾与复盘（PF-113、114；新增 PF-118 的复盘部分）

新增 closeout 存储/DTO/API；返回当前未完成任务、未验证标准、失败/部分通过/不确定/豁免项和待复查决策。保存草稿、生成复盘、完成收尾为不同操作。

复盘使用模板按已有事实生成 Markdown，保留来源和未知项，明确是待审阅草稿；复用 Wiki 编辑器。收尾只关联保存后的 Wiki ID，草稿不能被误标为正式知识。

用户确认目标结论及每个未解决项的处理方式后完成收尾；验证失败可结束，但事实保留。完成收尾不自动把需求置 DONE。完成前服务端重新检查当前标准及验证，避免用过期清单确认。

完成后若目标或验证改变，显示收尾结论需要复核，并提供重新打开路径；AI 使用与人工判断可选填，不调用外部 AI 服务。

验收：AC-13～16；未解决项无处置时不能完成收尾，有处置可完成；生成草稿不会直接保存/分享；保存失败仍保留修改；Wiki 关联和收尾权限一致。

### M7：MVP 完成验收（PF-115、116）

- PF-115 的测试分散在 M1～M6，M7 只做跨模块回归、迁移演练、构建与真实试用收口。
- 一条端到端路径：标题创建 → 定义并确认 → 阶段/任务标准 → 决策 → DONE 但未验证 → PASS → FAIL/PARTIAL → 修复并重验 → 处理未决项 → 审阅复盘并保存 → 完成收尾。
- AC-01～18 全部逐条记录结果；另覆盖阶段目标、AI 参与字段、标准变更、删除引用、旧后端接入和旧客户端字段保护。
- 前端执行 `npm run type-check`、`npm run build`；lint 使用不改写文件的命令。后端新增测试和迁移测试通过，并执行约定构建/格式检查。
- 数据库从含存量数据的 V1.0.5 升级及空库初始化均通过；验证新后端与旧客户端的基本需求、任务、Wiki 操作。
- 在一个真实需求上试用，记录重复填写、入口找不到、记录负担、证据不可达等问题，修复阻碍闭环的缺陷后再推进 P2。
- README、部署迁移指南、最低后端版本、功能关闭方式与真实实现一致。

## 8. 每个任务与 PR 的完成标准

每个任务记录 PF 编号、上下游依赖、API/migration/UI 改动、对应 AC、测试证据与剩余问题。按上述批次组织可审查 PR；跨仓库的同批 PR 相互关联。

用户约定：每批开发变更验证通过后，分别在涉及的仓库提交 commit 并 push 到当前开发分支；不将已完成的变更仅留在本地。推送前检查分支与远端状态，保持提交可追溯。

- 数据变更只新增 migration，不改已发布脚本；编号在实施时依据实际最新版本分配。
- 后端 PR 包含 DTO、校验、权限、字段更新兼容、迁移及关键测试；前端 PR 包含加载/空态/失败/保存/重试/冲突状态。
- 新功能在类型检查、构建之外有相应业务验收证据；“字段已加上”和“页面已画完”不单独表示功能完成。
- 上线顺序为备份与迁移演练 → 兼容的数据库增量 → 后端 → 前端 → 抽样回归。数据库问题优先前向修复，新功能可关闭。
- 开发预览沿用前端 `dev` 发布渠道；稳定版按既有发布流程进入 `main`，不在规划阶段指定或发布版本号。

第一批执行内容：PF-007 清理旧矩阵；PF-001 核对运行环境和迁移历史；PF-002～006 固定契约与业务规则；PF-120/121 建立兼容开关及最小测试基础。完成后进入 M1 问题定义。
